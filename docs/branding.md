# Branding

This document captures the early brand direction for MCP Toolkit and the wider
dr-w ecosystem.

## Umbrella Identity

The umbrella identity is **dr-w**.

The ecosystem should live under:

```text
dr-w.it
```

Products should be individual tools under the lab identity rather than a generic
startup-style AI brand.

Examples:

```text
inspector.dr-w.it
gateway.dr-w.it
auth.dr-w.it
```

## Origin

The `dr-w` identity comes from:

- the original nickname `wahrheit`
- the GitHub identity `dr-wahrheit`
- the idea of a personal engineering and devtools lab

This origin matters because it gives the project a more authentic and durable
identity than a generic AI startup name.

## Why dr-w

`dr-w` should feel:

- authentic
- technical
- old-school internet engineering
- open-source and devtools oriented
- experimentation-friendly
- developer-first

The brand should support a lab model: small, focused tools that solve real
developer problems in the MCP ecosystem.

## Positioning

MCP Toolkit should position itself as:

- DevTools for MCP
- debugging and inspection tooling
- developer-first MCP utilities
- security visibility tooling
- local-first workflows
- open-source-first adoption

MCP Toolkit should not position itself as:

- an enterprise orchestration platform
- a Kubernetes-first runtime platform
- a hosted AI automation suite
- a generic AI chatbot platform
- a low-code AI builder
- an agent marketplace
- another prompt playground

Security is a differentiator, but not the initial core product positioning. The
first product story should be inspection and debugging.

## Product Naming

Use clear tool names under the dr-w lab identity.

Current product:

```text
MCP Inspector
inspector.dr-w.it
```

Potential future products:

```text
MCP Gateway
gateway.dr-w.it

MCP Auth
auth.dr-w.it
```

Do not force every product name to include `dr-w`. The lab identity can live in
the domain, repository organization, documentation, and product footer.

## Naming Principles

Prefer names that are:

- direct
- technical
- descriptive
- easy to understand from the URL
- useful to developers without explanation

Avoid names that are:

- vague
- overly branded
- mascot-driven
- hype-oriented
- too clever for developer tooling

## Writing Style

Use writing that is:

- technical
- clean
- direct
- low on marketing language
- specific about workflows and constraints

Avoid:

- startup buzzwords
- AI hype wording
- enterprise corporate language
- inflated platform claims
- unnecessary complexity

## Philosophy

The dr-w ecosystem should feel like a serious engineering lab for practical
developer tools.

The first adoption goal is not revenue. It is trust, daily usefulness, OSS
visibility, developer feedback, and credibility with MCP server maintainers and
AI infrastructure engineers.
